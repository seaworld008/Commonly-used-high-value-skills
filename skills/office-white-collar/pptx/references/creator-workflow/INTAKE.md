# 把需求变成可以验收的演示任务

开始制作前，写下一句话：哪类听众在什么场景下，需要据此做出什么决定。
这句话决定证据深度、讲述顺序与交付形式。不要先用页数代替目标。

## 最小 brief
| 字段 | 要记录的事实 | 对制作的影响 |
| --- | --- | --- |
| 决策 | 本次要批准、选择或理解什么 | 结尾必须能回到同一个问题 |
| 受众 | 决策者、执行者、专业背景、已知疑问 | 决定术语解释和附录深度 |
| 场景 | 现场演讲、远程共享、会后独立阅读 | 决定字号、密度和讲稿长度 |
| 时间 | 可讲分钟数与讨论时间 | 按实际试讲长度调整页数 |
| 内容边界 | 必须覆盖、不能断言、仍待核实的事项 | 防止把假设写成事实 |
| 资产 | 已提供的数据、图片、品牌模板、字体 | 决定哪些页面能进入制作 |
| 交付 | PPTX、PDF、讲稿、源代码、数据及可编辑要求 | 决定技术路线和验收 |
| 运行条件 | 宿主可用工具、现有依赖、可用渲染器 | 决定实际执行方式 |

## 缺信息时怎样推进
先记录一个可逆的假设，再做不受该问题影响的整理工作。
例如，受众未知时可以先核对数据口径，不能据此声称适合董事会汇报。
会改变推荐结论的缺口应在 brief 中标为“待解决”，并在结论页保留不确定性。
已有授权足够时直接制作；此表本身不引入新的审批环节。

## 证据台账
给每条可核查断言分配证据 ID，例如 E-01。
记录来源文件及页码或工作表区域、作者/机构、发布或采集时间、单位、总体/样本、处理步骤。
网页证据保存准确 URL 与访问时间；离线材料记录版本或文件哈希。
区分原始测量、计算结果、外部估计和制作演示用的合成数据。
未知数据用“缺失/未提供”标识，不能用 0 代替。
图片、字体与模板还需记录使用许可及署名要求。

## 从问题到页面
先写三条听众可能追问的问题，再为每条问题安排证据或诚实的未知说明。
把需要共同理解的背景放在相关结论之前；熟悉背景的受众可从建议进入。
数字很多时先确定共同分母与比较基期，再考虑画图。
交付 brief 应引用[模板记录](TEMPLATES.md)，后续按[工作流](WORKFLOW.md)推进。
