# 生产操作安全

这些规则来自迁移过程中真实发生过的问题，都与"不影响业务"直接相关。

## 执行方式

- **长步骤脱离 SSH 执行**：有的主机 sshd 设置了 `ClientAliveInterval 300` 加 `ClientAliveCountMax 0`，5 分钟没有输出就会断开。切换脚本如果跑到一半被断开，会停在"旧服务已停、新服务未起"的状态。所以要在主机上执行 `setsid nohup bash cutover.sh > 日志 2>&1 < /dev/null &`，SSH 只用来轮询日志；客户端再加上 `-o ServerAliveInterval=30`。
- **不按进程名杀进程**：容器进程在宿主机上也能看到，`pkill -f php` 会误杀容器里的业务进程，甚至杀掉执行它的命令本身。先看 `/proc/<pid>/cgroup` 确认归属，再按 PID 处理；grep 模式写成 `[x]yz` 的形式，避免匹配到自己。
- **生成配置文件不手写**：用单引号写入 `$变量` 会把变量名原样写进文件，转发脚本到了 cron 的干净环境里就会失败。配置文件只由脚本生成，生成后用 `env -i PATH=/usr/bin:/bin` 模拟 cron 的环境，分别以 root 和业务用户验证。
- **整分钟避让**：每分钟都有定时任务的主机，会造成短暂空窗的操作（删包、替换程序）要从某分钟的第 5 秒开始做，并且控制在十几秒内完成。
- **一台一台做**：一台验证完，再做下一台。

## 诊断方式

- **只读优先**：先读日志、配置和进程，确认根因后再动手；改动前先备份，并把回滚命令写进主机上的 README。
- **读生产数据库**：
  - 只做定位问题所需的最小查询，会话设为只读（`SET SESSION TRANSACTION READ ONLY`）。
  - 凭据在进程内从应用配置读取，不打印到终端或日志。
  - 只输出汇总数字和非敏感字段，不输出用户身份、订单号、交易号。
- **逐台核实再下结论**：不要把一台主机的结论推广到另一台。例如"两台的邮箱都满了"这种说法，要分别查过每台每个用户的邮箱后才能写。
- **区分自己的操作和发布系统的操作**：看 `/var/log/secure` 的认证方式和来源 IP。比如自己用密码登录、CI 用密钥登录，就能分清哪些登录是发布系统做的。

## "一直失败的任务"不一定要修

迁移后看到某个定时任务退出码一直为 1，先别急着"修好"它：
1. 查出它在做什么：读命令代码和它自己的日志。
2. 弄清它卡在哪里，以及卡住的这一条后面还排着什么。
3. **量化"修好以后会发生什么"**：例如一个退款任务每次都卡在一条 0 元记录上，而它后面积压着几万条从来没有处理过的记录。只要把这一条修掉，任务就会开始批量发起真实退款，涉及金额可能很大。这种情况下，那条卡住的记录实际上起着熔断的作用。
4. 涉及资金或数据的任务，在负责人确认后只做停用（注释掉 crontab 里那一行，写明原因和"核对前不要恢复"），把积压记录交给业务方和财务核对。不改数据，不改代码。
5. 没有业务价值、只会一直失败的任务（例如 cd 到已删除目录的脚本），可以注释掉并写明原因。不要为了让它"成功"去改路径：如果它会修改历史数据，等于改变了业务行为。

## cron 的输出邮件

- 现象：邮箱达到 postfix 默认的 `mailbox_size_limit`（51,200,000 字节）以后，cron 的每一封输出邮件都会被退回。每分钟都有任务的主机，一天能产生几万次退信。
- 处理：在相关用户的 crontab 开头加 `MAILTO=""`，并加注释说明原因；邮箱压缩归档后清空（`truncate -s 0`，保持属主和权限不变）。这些输出原本就没人能看到，所以任务的行为不变。
- 验证：之后几分钟里 maillog 中 `status=bounced` 的数量为 0，任务的退出码与之前相同。

## 发布流程兼容性

迁移前后都要回答"发布还能不能用"：
- 读主机上的发布脚本，看它是否只做 rsync、`chown`、`nginx -t`，是否调用 php 或 composer，是否重启 php-fpm。
- 检查 `opcache.validate_timestamps` 和 `revalidate_freq`。为 1 时新代码会自动生效，不需要重载 FPM。
- 从 `/var/log/messages` 里查看历史上 php-fpm 的启停记录，判断发布是否会重启它。
- 迁移后至少确认一次真实发布：代码目录里的文件按时更新，属主正确，站点正常。
- `#!/usr/bin/env php` 开头、又不在挂载目录里的工具（composer）经转发后会找不到文件。确认发布流程不依赖这类工具；确实需要时，只读挂载该目录。

## 清理

- 旧安装目录先保留几天，作为最后一层回滚。删除前确认：没有进程的 exe、cwd 或映射文件指向它，配置和脚本里没有引用它，它也不是挂载点。
- 删除前把它的原配置打包、生成文件清单留档，再删除。删除后确认服务正常，并检查证书这类曾经放在该目录里的文件不再被引用。
- 失效的 systemd 单元（已停用、指向已删除的路径）移到备份目录，然后执行 `daemon-reload`。
