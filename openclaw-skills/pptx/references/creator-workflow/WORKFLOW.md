# 从 brief 到可复核交付

工作流以稳定的内容记录连接各步骤。每一步完成时留下可检查的产物，
随后步骤只依赖这些产物，不依赖某个特定 Agent 名称或平台工具。

## 1. 定义任务与证据边界
使用[需求入口](INTAKE.md)记录受众、决策、交付格式和数据来源。
把缺失事实、时间限制与未核实断言集中列在 brief 中。
输出：brief、证据台账、明确的可编辑要求。

## 2. 推导叙事
用“问题—发现—解释—选择—行动”检查论证是否闭合；顺序可随受众改变。
先写一行一页的断言，再为每页填写证据 ID、图示方案和听众可能提出的异议。
一页若包含两个互不支持的结论，就拆分或把次要结论移到附录。
推荐方案必须说明适用条件；不能把相关性写成因果。
输出：[页面卡片](TEMPLATES.md)与大纲。

## 3. 固定视觉系统
先选一张信息密度正常的内容页验证字体、留白和对比度。
按[风格规范](STYLE-GUIDE.md)定义字号层级、网格、颜色角色与页脚规则。
同样的语义在全套页面采用同样的颜色与标注方式。
输出：主题参数及一张样页，避免每页重新设计。

## 4. 选择制作路线
需要原生文本、形状、表格或可修改的数据图表时，直接使用已可用的
PptxGenJS 或 python-pptx，依照[制作说明](ORCHESTRATION_PPTX.md)构建。
需要迅速检验讲述顺序、交付主要为阅读稿时，可用已安装的 Marp 制作 Markdown 快速稿。
不要把 Marp 导出的 PPTX 或整页 SVG 自动认定为原生可编辑；交付前必须打开检查。
没有所选依赖时，交付已完成的大纲/源稿并准确说明缺口，或选宿主实际支持的路线。
输出：可重建源文件与制作版本记录。

## 5. 核对数据并生成页面
先做[数据校验](ORCHESTRATION_DATA_CHARTS.md)，再把图表插入页面。
对每页复核标题的断言是否由图中真实数据支持。
长文字优先删减、拆页或移入讲稿；不要用不断缩小字号解决溢出。
输出：PPTX 或快速稿、图表及输入数据、讲稿。

## 6. 渲染、评分、修复
用当前可用渲染器导出逐页图和 PDF，记录工具、版本与命令。
逐页检查原尺寸可读性和缩略图一致性；不能只检查封面。
按[评分表](RUBRIC.md)同时记录页面缺陷与整套评分。
每次修复后重查该页、前后页与共享主题影响的页面。
输出：缺陷清单、修复记录、最终评分及尚未执行的检查。

## 7. 包装交付
按[交付清单](CHECKLIST.md)核对文件、数据、来源、可编辑性与版本。
交付说明必须区分代码检查、实际渲染检查和目标桌面应用检查。
最终报告写明用途、已验证范围、剩余限制与文件位置。
